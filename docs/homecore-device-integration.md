# HomeCore device types and integration

Reviewed 20 November 2026 against HomeCore Core v0.1.120 and hc-web-svelte v0.1.85, both tagged on 19 November UTC. The frontend comparison between v0.1.84 and v0.1.85 contains no changes to the device/card sources examined here. This inventory describes the shipped examples and app behaviour. HomeCore accepts additional type strings from plugins and site profiles. ## Core's example type catalog

The shipped example defines 29 entries, including four compatibility aliases. Enabling it is a deployment configuration choice. A device can register with an explicit schema even when no catalog entry exists for its type. [Example catalog](https://github.com/homeCore-io/homeCore/blob/v0.1.120/config/profiles/examples/device-types.toml) · [Plugin registration and catalog docs](https://homecore.io/docs/plugins/overview/#plugin-device-registration)

| Family | All example-catalog entries | Native presentation in hc-web |
| --- | --- | --- |
| Switching | `switch`, `virtual_switch`, `vswitch` | On/off where the schema exposes a writable `on`. |
| Lighting | `light`, `dimmer_light`, `light_color`, `light_rgb` | `light` gets the dedicated light card and may show brightness and warmth. The three variants inherit the schema in Core and fall to the generic card unless presentation is set to `light`. |
| Room measurements | `temperature_sensor`, `temp_sensor`, `humidity_sensor`, `illuminance_sensor` | `temperature_sensor` gets a dedicated temperature/humidity summary. Humidity and illuminance still work as schema-driven readings. |
| Contacts and presence | `contact_sensor`, `motion_sensor`, `motion`, `occupancy_sensor`, `binary_sensor` | Contacts and presence have native status. Generic binary sensors use schema labels and leading readings. |
| Safety and movement | `smoke_sensor`, `water_sensor`, `vibration_sensor` | Wet/dry has a dedicated view, vibration has its own icon, and smoke/water reports can flag alarm state. |
| Electrical | `power_monitor` | The catalog describes a smart plug or inline meter and inherits `switch.on`. The type has a generic card. Native switch/outlet cards show watts when `power_w` is present. |
| Openings and locks | `cover`, `shade`, `lock` | Locks have a dedicated card. The Doors console recognises covers and uses the declared `open`/position write or exact open/close action when available. |
| Climate | `climate` | Groups under Climate in rooms. The dedicated thermostat renderers key on `thermostat`, which first-party HVAC plugins publish independently of this example catalog. [Thermostat plugin registration](https://github.com/homeCore-io/homeCore/blob/v0.1.120/plugins/hc-thermostat/src/bridge.rs#L305-L325) |
| Playback | `media_player` | Native media cards, transport, and volume where declared. |
| Timers | `timer` | Native countdown presentation. The first-party helper has timer-specific commands and actions. |
| Alarms | `siren` | The room console puts it with cameras and doorbells. Device controls depend on its schema. |
| Button inputs | `button` | Room placement recognises buttons. The example describes a physical input, while the core virtual button declares a press action. |
| General measurements | `sensor` | Generic card uses the declared primary readings. |

Presentation follows the [web card dispatch and alarm rules](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/card.ts#L230-L501), [room grouping](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/console/room.ts#L84-L187), [cover commands](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/console/doors.ts#L120-L135), and [helper schemas](https://github.com/homeCore-io/homeCore/blob/v0.1.120/crates/hc-core/src/glue/schema.rs#L62-L199).

Core trims and lowercases the type, and maps `vswitch` to `virtual_switch`, `temp_sensor` to `temperature_sensor`, `motion` to `motion_sensor`, `occupancy_group` to `occupancy_sensor`, and `shade` to `cover`. Other names survive normalization. Catalog `extends` inherits schema fields and leaves type identity independent. `climate` and `thermostat` therefore remain separate. [Type normalization and inheritance](https://github.com/homeCore-io/homeCore/blob/v0.1.120/crates/hc-topic-map/src/device_types.rs#L54-L150)

## What drives the UI

1. **Registration says what the device is.** Preserve stable `device_id` values and send the real `device_type` and room metadata when known. HomeCore stores the user’s name and room overrides separately. The web app’s own `kindOf` uses the user’s `ui_hint` before the registered type. [Core device model](https://github.com/homeCore-io/homeCore/blob/v0.1.120/crates/hc-types/src/device.rs#L264-L333) · [Web kind selector](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/card.ts#L230-L236)
2. **The schema says what this unit can report and do.** Declare leading readings in `primary`, use canonical names and units, and mark diagnostics, configuration, writable fields, and actions explicitly. The generic card gives a summary from up to two leading readings. It can expose a writable Boolean `on` or a single parameterless action, and on a large card it can add the next eligible slider or enum. The detail view uses the wider schema to show controls and history. Core writes the catalog-derived schema and the explicit plugin schema to the same slot. Publish registration followed by the full schema on discovery and reconnect so the adapter’s real limits take effect. [Device contract](https://homecore.io/docs/devices/overview/) · [Core schema write order](https://github.com/homeCore-io/homeCore/blob/v0.1.120/crates/hc-core/src/state_bridge.rs#L875-L912) · [Generic card rules](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/card.ts#L567-L607) · [Primary readings](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/card.ts#L748-L777)
3. **Slots own specific surfaces.** A `device.card` slot matches plugin owner and registered type, then the requested form and optional class `accepts()`; unavailable modules fall back to the built-in card. A `device.panel` provides a device detail section, with duplicates suppressed for certain kinds including `thermostat`. `dashboard.card` is independently placed by the user and suits multi-device views. HomeCore serves versioned, on-demand bundles and the installed module’s custom element tag is shared across the browser page. Adapter releases that share tags should ship the same bundle bytes. [Plugin screen contract](https://homecore.io/docs/plugins/plugin-screens/) · [Card precedence](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/components/DeviceCard.svelte#L35-L88) · [Slot matching and browser cache](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/pluginUi/uis.svelte.ts#L152-L210) · [Detail panel rules](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/components/Details.svelte#L50-L84)

## Native thermostat compatibility

The thermostat in the screenshot is the native Everywhere › Climate mini dial. Its room counterpart uses the same thermostat model. These console paths render their own thermostat controls and do not use the generic `device.card` slot selector. Their thermostat lists require a UI kind of `thermostat`, so assigning `climate` alone reaches the room's Climate tab without producing the same thermostat entry. [Everywhere Climate](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/console/EvClimate.svelte#L102-L121) · [Mini dial](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/console/ThermoMini.svelte#L30-L118) · [Room Climate](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/console/ClimateTab.svelte#L76-L96) · [Thermostat classification](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/console/climate.ts#L26-L44)

The native model reads `temperature`, `hvac_mode`, `hvac_action`, and the schema's targets. Declaring `setpoint` selects a single-target model even when heat and cool thresholds are also declared. The native nudge uses half degrees in °C or whole degrees in °F and converts back without snapping to the adapter's raw step. The Rooms and Everywhere buttons check permission, online state, target value, and min/max. They do not check target writability or HVAC mode. Both surfaces must be included when testing a type change. [State, target and step logic](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/thermostat.ts#L54-L157) · [Room nudge](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/console/Thermo.svelte#L164-L194) · [Everywhere nudge](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/console/ThermoMini.svelte#L104-L119)

Keep the shared card and expanded controls for airflow, the Auto gap and controller confirmation. [Registration and schema](../services/mitsubishi/src/bridge.rs) · [Command limits](../services/mitsubishi/src/control.rs) |
| Electrolux | `thermostat`, with a 17–30 °C whole-degree setpoint, mode, fan and vertical swing. The published status has mode and power but no `hvac_action`. | Keep its type and the shared card. A selected mode expresses intent. Publish active heating or cooling only when controller data establishes it. [Registration, schema and state](../services/electrolux/src/bin/electrolux-bridge.rs) |
| Powerwall and site energy | One read-only `sensor` for site flows, charge, tariffs and dated energy. Its device card selects the Powerwall by ID. | Keep the combined device and energy cards. Consider a dedicated meter only where there is a distinct measured role, such as a real grid meter. [Powerwall registration and schema](../services/teslemetry/src/bin/teslemetry-bridge.rs) · [Power flow and card selection](../services/teslemetry/ui/index.js) |
| Tesla vehicles | One read-only `sensor` per discovered car. The schema leads with reported battery level and vehicle state. | Use the native schema summary for now. If a vehicle card is needed, give it an explicit vehicle match and show charging or range only when reported. [Vehicle schema and registration](../services/teslemetry/src/vehicle.rs) |
| Wall Connector | Dated site sum under `wall_connectors_energy_wh` when provided. | Use the dated total as an optional energy reading. An individual charger entry with live power or controls needs per-connector identity and real connector telemetry. [Connector totals](../services/teslemetry/src/totals.rs) |

The native thermostat check ran the actual v0.1.84 model functions with simulated adapter data. One + press from an Electrolux target of 21 °C generated `21.5` in Celsius display and `21.11` in Fahrenheit display, both in raw Celsius. The Electrolux bridge accepts only whole degrees in range. With the Mitsubishi-style mixed schema in Auto, the native model selected `setpoint` even when both thresholds were present. The Mitsubishi bridge accepts the single target in Heat and Cool, and the separate thresholds in Auto. These checks exercised the frontend model only. ## Recommended order

1. **Place each AC in its room.** Assign its room in HomeCore, or publish an optional `area` from adapter configuration where known. Preserve existing device IDs and user overrides. This addresses the “No room” label independently of card styling and type changes. [Device registration and override fields](https://homecore.io/docs/devices/overview/) · [Room Climate view](https://homecore.io/docs/web-ui/rooms/#the-tabs)
2. **Align native climate controls before reclassifying Mitsubishi.** Test Home, Rooms › Climate, Everywhere › Climate and device details against both adapters. The native controls should step and clamp in raw schema units, choose the mode's writable target, and handle mixed single/dual schemas. Include display in °C and °F, Off, offline, read-only permissions, mode switches, and the Mitsubishi Auto minimum gap. Then pilot `thermostat` on one existing Mitsubishi ID, verify its room, history, rules and card slots, and check whether the panel should include a short history chart when the generic chart is suppressed. [Thermostat model](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/thermostat.ts#L54-L157) · [Panel history suppression](https://github.com/homeCore-io/hc-web-svelte/blob/v0.1.85/src/lib/components/Details.svelte#L623-L655)
3. **Make sensor and energy schemas more informative.** Keep `primary` small, add clear names and units, and mark controller metadata and signal readings as diagnostic where appropriate. Use `power_w` or `energy_kwh` for a specific meter when the quantity and time basis match. Preserve Powerwall's signed branches and dated Wh fields, and preserve zero and negative tariff values as well as missing rates. Avoid aliasing stationary or vehicle charge to `battery_pct` unless household low-battery alerts are intended. [Device vocabulary and schema](https://homecore.io/docs/devices/overview/) · [Battery alerts](https://homecore.io/docs/devices/battery-monitoring/) · [Current tariff semantics](tariffs.md)
4. **Use native UI wherever the schema is sufficient.** For future switches, lights, sensors, covers and media devices, start with the real device type and capabilities. Add a plugin card or panel when a device needs controls the generic UI cannot express well, such as vane settings or a dual setpoint with a gap. Use a dashboard slot for combined energy and a look drawing only if the goal is to change a selectable app theme's depiction. Use the generic automation editor first and add a `rule.step` when a specialised action needs a better form. [Plugin slots and rule-step contract](https://homecore.io/docs/plugins/plugin-screens/) · [HomeCore Looks](https://homecore.io/docs/web-ui/looks/)
